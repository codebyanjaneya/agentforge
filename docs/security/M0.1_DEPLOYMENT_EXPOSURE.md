## 1. Executive summary

- The production API hostname **is unambiguously identified in the repository**: `65-0-30-8.sslip.io` (resolves to `65.0.30.8`), hard-coded in four frontend files since commits `de0fe86` (2026-06-22) and `228fa50` (2026-06-23).
- **Public exposure of the API could NOT be established.** From this machine, TCP connections to ports 443 and 80 of `65.0.30.8` **timed out** (no response, no reset). A control request to an unrelated HTTPS site succeeded, so the machine's network works. A timeout is not evidence of safety: it is consistent with a stopped/terminated instance, a security group that allows only specific source IPs, an ISP/route issue to that range, or a service on another port. I did not probe other ports.
- **Cloud inspection was not possible.** AWS CLI v2 is installed with a `default` profile (region `ap-south-1`), but `aws sts get-caller-identity` returned `InvalidClientTokenId` — the locally stored credentials are invalid or expired. No EC2/security-group/ELB data could be read.
- **The repository contains zero deployment configuration** (no Dockerfile, Compose, NGINX/Caddy, systemd, CI, scripts, Terraform). The production topology cannot be derived from the repo; it is inferred only from URLs.
- **Code-level exposure is fully verified** (see §6, §7): if the API at that hostname is running this code — which is **not** verified — the Twilio SSRF/credential leak, forged Telegram linking, group-chat processing, and unauthenticated WebSocket/REST are all live, because there is no feature flag, auth or proxy rule in the repo that could be disabling them.
- **Safest next action:** have the owner confirm the instance state and exposure (see §9), and in parallel authorize the minimal-risk code-level containments (disable `/voice/*`, disable `/link <email>` + base64 `/start`, private-chats-only) — these do not depend on knowing the proxy configuration. If the instance is running and reachable, also rotate the Twilio auth token and Telegram bot token (they cannot be proven uncompromised).

## 4. Public reachability results (performed)

Target: `65-0-30-8.sslip.io` (identified from repo). Total of **6 connection attempts** to the target (health, three docs paths, TLS handshake, port 80), all GET/handshake-level, short timeouts (6–10 s), no body sent, no authentication attempted.

| Check | Result |
|---|---|
| DNS (`nslookup`) | Resolves to `65.0.30.8` |
| `GET https://…/health` | **Connection timed out (8 s)** — no HTTP response |
| `GET https://…/docs`, `/openapi.json`, `/redoc` | **All timed out** — docs exposure **not determinable** |
| TLS handshake / certificate (`openssl s_client`, SNI) | **No certificate retrieved** (connection never established) — validity and hostname match **not determinable** |
| `GET http://…/health` (port 80) | **Timed out** |
| WebSocket handshake to `/ws` | **Not attempted**: the TLS port was unreachable, so there was nothing to handshake with; I did not try other ports or routes |
| Control: `GET https://example.com` | `200` — local network OK |

**Interpretation (do not treat as "safe"):** silent timeout on both 80 and 443 usually means packets are dropped (security group/firewall/NACL, stopped instance with no route, or an IP-restricted allow-list that excludes this client). It does **not** show the service is down, nor that it is unreachable from other networks (e.g. Vercel, Twilio, Telegram, attackers on allow-listed ranges). Because the dashboard's WebSocket goes browser → `wss://65-0-30-8.sslip.io`, a working deployment would have to be reachable from arbitrary user networks, which suggests either the instance is currently stopped/changed or reachability is network-dependent — **unresolved**.

## 5. TLS / reverse proxy / WebSocket findings

- **Verified:** the client expects TLS on 443 with a hostname-valid certificate for `65-0-30-8.sslip.io` (browsers will enforce it) and WS upgrade at path `/ws`. The repo contains no proxy config, so any statement about NGINX, certificates (Let's Encrypt via sslip.io is a common but unconfirmed pattern), HTTP→HTTPS redirect, `Upgrade`/`Connection` header forwarding, request-size limits, timeouts, access logs, or header sanitization is **unverified**.
- **Application-level (verified in code, independent of the proxy):** `/ws` accepts any origin and any connection; FastAPI `/docs`, `/redoc`, `/openapi.json` are enabled; CORS allows only `http://localhost:3000`; there is no `X-Forwarded-*`/trusted-proxy handling (the app does not use client IPs today, so rate-limiting by IP would need that later).
- **Risk if exposed:** the application port may also be reachable directly (e.g. 8000, where README's `uvicorn --port 8000` runs it), bypassing any proxy rules. Unknown until security groups are reviewed.
