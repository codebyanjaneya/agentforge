# AgentForge operations runbook (sprint 2)

Status of every procedure below is stated. **"Drilled"** = executed against a disposable local resource in sprint 2 (evidence in `flow.md` §25.31). **"Documented"** = written but never executed. Nothing here has been run against production, staging or a live credential.

## 1. Processes and startup / shutdown

| Process | Command (from `backend/`) | Notes |
|---|---|---|
| API | `uvicorn main:app --host 0.0.0.0 --port 8000` | `RUN_EXECUTION=embedded` (default) drives plan runs in this process; `api-only` leaves runs unclaimed for workers. |
| Worker | `python worker.py` | Claims runs with a lease; any number may run. Needs the same `DATABASE_URL`, `REDIS_URL`, model key. |
| Migrations | `python -m alembic upgrade head` | Run once per release, BEFORE starting new code. The API refuses to start on a database whose revision is not the code's head (`schema_guard`). |

Start order: PostgreSQL, Redis, migrate, API(s), worker(s). Stop: send SIGTERM/Ctrl-C; a process that stops mid-run closes what it owns as `interrupted`/`unknown` (never `cancelled` for a dispatch that may have been sent); another process recovers the rest after the lease TTL. Do not `kill -9` on purpose: it works (lease expiry + recovery are tested) but delays recovery by the lease TTL.

## 2. Health and readiness

* `GET /health` — liveness only (process answers). Never limited, no dependencies.
* `GET /ready` — readiness: the database answers `SELECT 1`; 503 `{"status":"unavailable"}` with no detail otherwise (the cause is in the log). Use it for load-balancer routing, not `/health`.
* `GET /metrics` — only when `METRICS_TOKEN` is set; send `Authorization: Bearer <token>`. 404 otherwise. Scrape **every** API and worker process (counters are per process); gauges come from the database.

## 3. Configuration and secrets checklist (names only; never commit values)

Required in production: `APP_ENV=production`, `DATABASE_URL` (PostgreSQL, TLS), `REDIS_URL`, `GROQ_API_KEY`, `CORS_ALLOWED_ORIGINS` (exact origins), `AUTH_CONFIG_REQUIRED=1` + `AUTH_JWT_PUBLIC_KEYS` (kid → PEM), `AUTH_JWT_ISSUER` / `AUTH_JWT_AUDIENCE` if non-default.
Frontend (server side only): `NEXTAUTH_SECRET`, `NEXTAUTH_URL`, `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`, `BACKEND_TOKEN_PRIVATE_KEY` (+ `BACKEND_TOKEN_KID`), `NEXT_PUBLIC_API_BASE` (https, bare origin).
Optional: `RUN_EXECUTION`, `METRICS_TOKEN`, `LOG_FORMAT=json`, `PROVIDER_MAX_ATTEMPTS`, `PROVIDER_BASE_DELAY`, `PROVIDER_MAX_WAIT`, `PROVIDER_BUDGET`, `PROVIDER_CONCURRENCY` (per process), `PROVIDER_GLOBAL_CONCURRENCY` (all processes, default 8), `PROVIDER_ADMISSION_WAIT` (default 30 s).
Must be OFF in production: `AGENTFORGE_DEMO_MODE` (the app refuses to start with it), API docs unless deliberately enabled.
Before go-live check: every secret comes from the platform secret store (not a file in the image); `METRICS_TOKEN` is set and not reachable from the internet; Redis is not publicly reachable; the reverse proxy limits unauthenticated traffic (the app only limits authenticated users, D070) and sets `--ws-max-size`.

## 4. Backup and restore (PostgreSQL) — **Drilled** on a disposable container

Backup (custom format, consistent snapshot, no downtime):
```
pg_dump -Fc -f agentforge-$(date +%Y%m%d%H%M).dump "$DATABASE_URL"
```
Restore into a NEW database (never over the live one), verify, then switch traffic:
```
createdb agentforge_restore
pg_restore --no-owner -d agentforge_restore agentforge-….dump
python -c "from migrations.schema_guard import verify_schema_version as v; print(v('postgresql://…/agentforge_restore'))"   # prints the head revision
```
Verify: table count and row counts equal the source for your key tables (`users`, `plans`, `plan_runs`, `tool_dispatches`), `alembic_version` equal. Redis holds only short-lived state (rate-limit windows, provider cooldown/slots, short-term chat memory): it is NOT backed up and may be flushed; the cost is a brief loss of those windows and chat context.
Frequency/retention are a deployment decision (not set here). Point-in-time recovery (WAL archiving) is **Documented only** (needs the hosting provider's feature).

## 5. Migration rollback — **Drilled** (0016 down → up with data intact)

Prefer rolling FORWARD. If a release must be reverted: stop new code; `python -m alembic downgrade <previous revision>`; deploy the previous code. Downgrading `0016_durable_dispatch` drops `tool_dispatches` and `tool_reconciliations` (the dispatch ledger and every reconciliation record): **take a dump first** and do not downgrade while any dispatch is `unknown` (you would lose the only record that an external action may have happened). Re-upgrade restored the schema and kept all other data in the drill.

## 6. Release checklist

1. CI green (`.github/workflows/ci.yml`: per-file backend tests, PostgreSQL job, frontend tsc/eslint/test). 2. Dump the database. 3. Apply migrations on a staging copy first (restore the dump there, `alembic upgrade head`). 4. Deploy API/worker. 5. `GET /ready` 200 on every instance; one `GET /metrics` scrape. 6. Smoke: sign in, create a plan, run it, approve, see the run succeed (the demo mode journey in `docs/demo.md` does this with no live credentials; it must be run on STAGING with demo mode, never production). 7. Rollback trigger: readiness failing > 5 min, or `agentforge_dispatch_unknown_total` rising unexpectedly → section 5 / 8.

## 7. Failure diagnosis

* **A run did not finish:** `GET /plan-runs/{id}` and `/plan-runs/{id}/events` (append-only history: who did what, lease takeovers, recoveries). A run with no owner after the lease TTL is recovered by any live process; none live → start a worker.
* **A task failed `side_effect_outcome_unknown`:** an external action may have happened. Do NOT retry. Open the run page → Side effects → reconcile (ask the remote service, or record a decision with evidence). The invocation and dispatch rows (`tool_invocations`, `tool_dispatches`, `tool_reconciliations`) are the evidence.
* **Many 429 `too_many_requests`:** a per-user limit (D070); `Retry-After` says when. **429 `rate_limited` on a model call:** provider limit or the global slots (D071) — see `provider_events` rows of the run and `agentforge_provider_events_total`.
* **Provider errors:** `GET /plan-runs/{id}/provider-events`; usage limits longer than the maximum wait end as `exhausted`, not slept through (D065).
* **Not ready:** `/ready` 503 → database unreachable: check the log line `readiness probe failed`.
* **Logs:** `LOG_FORMAT=json`; filter by `run`, `task`, `execution`, `workspace`. Messages never contain tokens or tool arguments.

## 8. Incident runbook (first 15 minutes)

1. Stop the bleeding: if a tool is misbehaving, disable it (tool lifecycle → `disabled`) rather than the whole API. 2. If duplicate or unexpected external actions are suspected, query `tool_dispatches WHERE state IN ('unknown','dispatching')` — these are the actions whose effect is unproven; reconcile each, never re-run. 3. If the database is suspect, take a dump before anything else. 4. Roll forward if you can, roll back by section 5 if you must. 5. Write down: time, run ids, dispatch ids, what was reconciled and by whom (the reconciliation records already store actor, evidence and reason).

## 9. Load baseline

See `flow.md` §25.31 for the measured numbers and their conditions (local, SQLite, single process). It is a baseline for regression comparison, **not** a capacity statement.


## 10. Redis failure behaviour (sprint 3) — **Drilled** against a real Redis container (`backend/tests/ops/redis_failure_drill.py`, 13 checks)

| Feature | Redis unreachable | What you will see | Redis back |
|---|---|---|---|
| Per-user rate limits (D070) | **Degrades**, never unlimited: a bounded per-process counter takes over, a 15 s breaker stops per-request connection attempts | `agentforge_redis_unavailable_total{feature="rate_limit"}`; one warning per outage. The budget is no longer shared: N processes admit up to N x the limit | shared counting resumes at the next window |
| Provider cooldown and global cap (D071), `PROVIDER_REDIS_DOWN=degrade` (EXPLICIT opt-in since sprint 4.1; it was the default before) | Falls back to per-process limits (`PROVIDER_CONCURRENCY`): requests are served, the global cap and the shared cooldown are NOT enforced (measured: provider concurrency 6-7 against a cap of 4) | `agentforge_provider_admission_total{decision="degraded"}`, `agentforge_redis_unavailable_total{mode="degrade"}`, gauge `agentforge_provider_global_cap_enforced` = 0, alert `AgentForgeProviderCapNotEnforced`, a start-up warning that the mode was chosen | sharing resumes after the breaker interval (and after the quarantine, below) |
| `PROVIDER_REDIS_DOWN=closed` (the DEFAULT since sprint 4.1) | **Fails closed**: no global slot is granted; a request waits `PROVIDER_ADMISSION_WAIT` (30 s) then fails as `rate_limited`, the provider is never called | same metric with `mode="fail_closed"`; runs fail with the existing honest `rate_limited` code | requests are admitted again |
| Short-term chat memory (existing) | The chat features that use it fail (no fallback in the code; not drilled); plan/run/approval paths do not use Redis | errors in those routes | recovers by itself |
| `/health`, `/ready` | unaffected (`/ready` checks the database only) | - | - |

Choose `closed` when exceeding the provider quota is worse than refusing work (a paid, rate-billed key); keep `degrade` when availability matters more. Neither mode is silent: the outage is counted and alerted (`AgentForgeRedisUnavailable`).
**State after a restart:** a graceful restart keeps leases and cooldowns (Redis writes its RDB on SIGTERM; verified). A Redis restarted WITHOUT persistence, or killed between saves, forgets live slot holders, so the cap can be exceeded by the in-flight requests until their leases (180 s) expire; a cooldown is forgotten (the next 429 sets it again). Leases of a crashed holder are reclaimed by expiry (verified with a 0.5 s lease). **Not tested:** Redis Sentinel/Cluster failover and client reconnection behaviour on a real failover; there is no such topology locally. The Redis client reconnects per call and the breaker re-probes every 15 s, so the expected behaviour is "degrade for up to ~15 s after the new primary is reachable", unverified.

## 11. Rate-limit and provider configuration (sprint 3)

All values are validated at start-up (out of range = refuse to start, naming the variable, never echoing the value). Defaults are in `config.RATE_LIMIT_DEFAULTS` / `PROVIDER_BOUNDS`.

| Variable | Default | Range | Meaning |
|---|---|---|---|
| `RATE_LIMIT_PLAN_CREATE` | 15 | 1-6000 | plan creations per user per minute (a model call each) |
| `RATE_LIMIT_PLAN_REVISE` / `_PLAN_APPROVE` | 40 / 40 | 1-6000 | |
| `RATE_LIMIT_RUN_START` / `_RUN_RETRY` | 15 / 15 | 1-6000 | |
| `RATE_LIMIT_APPROVAL_DECIDE` | 40 | 1-6000 | approvals approved/rejected |
| `RATE_LIMIT_RECONCILE` | 20 | 1-6000 | reconciliation attempts |
| `RATE_LIMIT_AGENT_RUN` / `_IMPROVE` | 30 / 6 | 1-6000 | direct agent runs / self-improvement |
| `RATE_LIMIT_WS_CONNECTS` / `_WS_JOBS` | 30 / 30 | 1-6000 | per user, across all of that user's sockets and processes |
| `PROVIDER_MAX_ATTEMPTS` | 4 | 1-10 | attempts per model request |
| `PROVIDER_BASE_DELAY` / `_MAX_WAIT` / `_BUDGET` | 1 / 90 / 240 s | 0.01-60 / 1-600 / 1-1800 | backoff base, longest single wait, total waiting per request |
| `PROVIDER_CONCURRENCY` | 2 | 1-64 | simultaneous requests per process |
| `PROVIDER_GLOBAL_CONCURRENCY` | 8 | 1-256 | simultaneous requests across ALL processes (Redis) |
| `PROVIDER_ADMISSION_WAIT` | 30 s | 0-300 | longest wait for a global slot |
| `PROVIDER_REDIS_DOWN` | `closed` | `closed`/`degrade` | section 22 (`degrade` is an explicit opt-in and is warned about at start-up) |
| `PROVIDER_LEASE_SECONDS` | 90 s | 30-900 | a provider slot lease AND the post-failover quarantine: must exceed the longest single provider call (60 s default timeout) plus margin |
| `TOKEN_ISSUE_PER_MINUTE` (frontend, server side) | 30 | 1-600 | access tokens issued per signed-in person per minute (invalid value = default, never "off") |

**What the application does NOT protect (edge requirement).** The limits above apply to AUTHENTICATED users. A flood of unauthenticated requests (invalid tokens, unknown paths, WebSocket handshakes before authentication, `POST /api/backend-token` without a session) costs the server work before any identity exists and cannot be counted per person. The reverse proxy / CDN in front of the API and the Next.js app MUST limit by client IP and connection count (and set a WebSocket max message size, `--ws-max-size`, and TLS). Behind a proxy, configure it to pass the real client address; none of this is verified here because no edge exists in this repository.
**Token issuance (`/api/backend-token`).** It already refuses cross-origin, unauthenticated and unverified callers. Sprint 3 added a per-person ceiling (30/min by default, in memory per Next.js process: no new cross-stack dependency, so N Next.js instances allow N x the limit).

## 12. Alerts (sprint 3) — **defined and tested against the code, NOT LIVE**

`ops/alerts/agentforge-alerts.yml` (Prometheus rule format, 16 alerts): instance down, not ready, 5xx rate, p95 latency, unresolved/rising unknown side-effect outcomes, approval backlog, failing/interrupted runs, lease takeovers, no workers while runs wait, provider retry budget exhausted, Redis unavailable, DB pool near exhaustion, sustained rate limiting, backup stale, restore verification failed. `backend/tests/test_alert_rules.py` keeps them honest: every rule is well formed and every metric it queries exists in the code or is declared external. Two alerts depend on metrics the BACKUP/RESTORE JOBS must publish (`agentforge_backup_last_success_timestamp_seconds`, `agentforge_restore_verification_ok`); the application does not emit them and no such job exists yet. No monitoring backend is configured in this repository, so nothing pages anyone today. Thresholds are starting points, not measured SLOs. promtool was not run.
**Per process vs aggregated:** every counter and histogram is per process; aggregate with `sum()` across instances (the rules do). The gauges (`runs_running`, `dispatch_unresolved`, `approvals_pending`, `workers_registered`) are read from the database at scrape time and are the same from every instance, so use `max()` or a single instance's value, not `sum()`. `db_pool_*` gauges are per process. Labels are a fixed vocabulary (status class, error code, decision, provider event kind, route TEMPLATE, bucket, feature): never a user, workspace or run id, never a token or a raw path.
**Correlation (logs, `LOG_FORMAT=json`):** `workspace`, `run`, `task`, `execution`, `invocation`, `approval`, `provider_request` (one id per logical model request, shared by its retries), `dispatch`. They let you follow plan -> task -> agent execution -> tool invocation -> approval / reconciliation by grepping one id. Distributed tracing (OpenTelemetry) was NOT added: the stack has no collector and the id correlation already covers the single-service lifecycle.

## 13. Point-in-time recovery (PITR)

**Design.** Continuous WAL archiving plus periodic base backups, restored to a chosen instant. Requirements: `wal_level=replica` (or higher), `archive_mode=on`, an `archive_command` that is atomic and idempotent (copy to durable, access-controlled storage in another failure domain; never overwrite a file), `archive_timeout` (60-300 s; bounds data loss when traffic is low), base backups at least daily (`pg_basebackup`, or the managed service's snapshot), WAL retention covering the oldest base backup you may need, encryption at rest and in transit, monitoring of archive lag/failures (`pg_stat_archiver`). On a managed PostgreSQL service use its PITR feature and verify its retention window instead of running this yourself.
**Assumptions (to be confirmed by the owner, none are decisions):** RPO of 5 minutes or less with `archive_timeout=300` (worst case: the unarchived tail of one segment; with streaming replication/managed PITR typically seconds); RTO of one to two hours for a database of tens of GB (restore base + replay WAL; **not measured** at that size). Logical `pg_dump` (section 4) is for migrations and small restores; it is not a substitute for PITR.
**Retention and verification policy (proposal):** base backups daily, kept 14 days; WAL kept for the same window; a monthly dump kept 12 months; every backup is restored automatically to a scratch database weekly and checked (schema head, row counts of key tables, a smoke query), and its success is published as `agentforge_restore_verification_ok` and `agentforge_backup_last_success_timestamp_seconds`.
**Restore procedure:** never restore over the live database. (1) Decide the target instant (just before the mistake). (2) New data directory from the latest base backup taken BEFORE that instant. (3) `touch recovery.signal`; set `restore_command` (copy from the archive), `recovery_target_time`, `recovery_target_action = 'promote'`. (4) Start, wait for `pg_is_in_recovery() = f`. (5) Verify (schema head, row counts, the rows you expect on both sides of the instant). (6) Point a staging copy of the application at it, then switch traffic.
**Drill — Drilled locally, disposable Docker only** (`bash ops/pitr_drill.sh`, removes its own containers and volumes): archive on, base backup, 100 rows before the target instant T, 100 rows after; restoring to T returned exactly 200 rows with 0 rows from after T. NOT proven: retention, off-host archive, encryption, restore time at production size, a managed provider's PITR.
**Staging restore drill (UNVERIFIED — needs an authorised staging environment, none is available):** (1) take a production-equivalent backup/WAL set into staging storage (never the other direction); (2) restore it to a new staging database with the procedure above, to a target instant 30 minutes in the past; (3) run `alembic current` (must equal the deployed head) and `verify_schema_version`; (4) start ONE API process and ONE worker with `AGENTFORGE_DEMO_MODE=1` and a placeholder model key, `METRICS_TOKEN` set; (5) `GET /ready` 200, `GET /metrics`, sign in with a test user, open the newest plan and run, check `agentforge_dispatch_unresolved` equals the number of `unknown` dispatches in the data, reconcile one if any; (6) record wall-clock time of each step (this is the first real RTO number) and the size restored; (7) destroy the staging database; (8) file the findings. Nothing in steps 1-8 has been executed.

## 15. Test-run hygiene and a known timing sensitivity (sprint 3.1)

* **Always keep the full pytest output** of a regression (`> file 2>&1`, then summarise), never only `tail -1`: the original final-tree run lost the name of its one failing test (`test_run_recovery.py`) and it could not be diagnosed afterwards.
* **Lease-timing tests are sensitive to starvation.** `tests/test_run_recovery.py` uses real leases of 0.9 s and 2.0 s with sub-second heartbeats; on a machine with little free memory or CPU a heartbeat can be delayed past the lease term, which is correct product behaviour (a stalled owner loses its run, proven by `tests/test_run_recovery_stall.py`) but fails a test that assumes the owner stays healthy. Run the suite on an otherwise idle machine, one file at a time; a recurrence should be diagnosed from captured output before anyone widens a timeout.
* **Windows:** a venv `python.exe` is a launcher that spawns the real interpreter; test helpers that signal, suspend or kill a child must act on the whole process tree (`taskkill /T`).
* **Clean PostgreSQL run recipe (verified):** fresh `postgres:16` container on a loopback non-default port with `-c agentforge.disposable=<token>`, then `AGENTFORGE_TEST_PG_ADMIN_URL=... AGENTFORGE_TEST_PG_TOKEN=... python -m pytest tests/test_postgres_integration.py -v --durations=10 -p no:cacheprovider -W error::pytest.PytestUnhandledThreadExceptionWarning` (64 passed in 222 s on the 2026-11-20 final tree); edit nothing while it runs.


## 16. The real email integration `email.send@1` (sprint 4)

**What it is.** The first REAL side-effecting tool: it sends one plain-text email through Resend (`POST https://api.resend.com/emails`). It exists only when `RESEND_API_KEY` is set; `EMAIL_FROM` is then required. Every call needs a workspace owner/admin to approve that exact call (recipient, subject, text); the tool is not on the auto-run allowlist. The simulated `demo.send_note` is unchanged and still labelled SIMULATED.
**Sandbox by default.** Recipients must belong to `EMAIL_ALLOWED_DOMAINS` (default `resend.dev`, Resend's test addresses `delivered@`, `bounced@`, `complained@`, `suppressed@resend.dev`). Real recipients need an explicit operator decision (`EMAIL_ALLOWED_DOMAINS=yourcompany.com`) and are NOT enabled by any default.
**What Resend documents (read from resend.com/docs on 2026-11-20) and what AgentForge relies on.** `Idempotency-Key` header, 1-256 characters, kept 24 hours: the same key with the same payload returns the original response without sending again; the same key with a different payload is `409 invalid_idempotent_request`; a concurrent request with the same key is `409 concurrent_idempotent_requests`; a bad key length is `400 invalid_idempotency_key`. `GET /emails/{id}` returns the email and its `last_event`. **Not documented, therefore not relied on:** lookup by idempotency key, the full list of `last_event` values on the page read, what a missing id returns.
**The guarantee, stated exactly.** (1) AgentForge dispatches at most ONCE automatically per logical operation (D066/D067) and never retries an unknown outcome. (2) It sends the operation's STABLE idempotency key, so a duplicate request that somehow escaped (inside 24 h) would be deduplicated by Resend, **as documented but not independently verified against the live service**. (3) It does NOT guarantee exactly-once delivery: acceptance is not delivery, the key protects only 24 hours, and an unknown outcome (timeout, lost response, 5xx, 409) can only be reconciled by a person checking the Resend dashboard or `GET /emails/{id}` and recording what they saw (an attestation, never proof): no key-based lookup exists, so the "ask the remote service" reconciliation button reports it cannot ask. Replaying the same key to "ask" Resend is deliberately not offered: it would dispatch under a reconciliation record.
**Outcome mapping.** 2xx with an id = success (the id is the external reference); 400/401/403/404/422/429 = definitive failure (nothing sent); 409, 5xx, timeouts, connection errors, unreadable 2xx = UNKNOWN.
**Secrets.** The key is read once from the environment into a `SecretStr`, held only inside the tool module, sent only in the Authorization header to one fixed https host; it is in no tool input/output, event, log or error (test-verified). A non-https provider URL is refused outside tests; redirects are refused.
**Verified vs unverified.** Verified locally: 19 contract tests against a LOCAL mock that models only the documented semantics, plus runtime tests through the real durable-dispatch protocol (a lost response becomes `unknown`, blocks the retry and is never re-sent), and a load run in which the email tool sent through two API processes and two workers to the mock with 0 duplicate sends. **NOT verified: any real call to Resend.** Credential/configuration checklist to run it for real in a SANDBOX: (1) create a Resend account and an API key restricted to sending; (2) verify a sending domain, or use the `onboarding@resend.dev` sender Resend documents for testing; (3) set `RESEND_API_KEY`, `EMAIL_FROM` in the secret store (never `backend/.env` in a shared repository); (4) leave `EMAIL_ALLOWED_DOMAINS` unset; (5) grant `email.send` to one test agent; (6) run a plan whose task requires `email.send@1` and approve it, sending to `delivered@resend.dev`; (7) confirm in the Resend dashboard that exactly one email exists; (8) re-run the same task to observe the replay (the second run must not create a second email); (9) record the observed behaviour here. Only after that may the "documented" statements above be upgraded to "verified".

## 17. Edge security and deployment configuration (sprint 4)

**Two layers, kept distinct.** Per-USER limits live in the application (D070, Redis-shared). Per-IP flood protection for UNAUTHENTICATED traffic lives at the edge: `ops/nginx/agentforge.conf` (nginx >= 1.25) is a production example with per-IP request and connection limits (token issuance and sign-in strictest), WebSocket handshake limits, `client_max_body_size`, header/body/send timeouts, `X-Forwarded-For` OVERWRITTEN (never appended), TLS 1.2+ only with HSTS, HTTP to HTTPS redirect, `/metrics`, `/docs`, `/redoc`, `/openapi.json` answered 404, `/ready` only for private ranges, 429 with `Retry-After`. Run `bash ops/edge_drill.sh` to exercise it in a real nginx container: **13 of 13 checks passed** (syntax, redirect, TLS 1.1 refused, TLS 1.2 ok, hidden endpoints, XFF overwrite, 413 for a 2 MiB body while 5 KB passes, WebSocket upgrade headers reach the upstream, 29 of 40 token-issuance requests from one IP refused with 429 and Retry-After, 386 of 500 API requests on one connection refused, independent zones). **Not proven:** behaviour behind a CDN, real certificates, IPv6, a distributed (many-IP) flood, the `/ready` deny path (from the drill host the source is Docker's private gateway).
**Application protections (defence in depth, tested):** `MAX_REQUEST_BYTES` (default 1 MiB, 1 KiB-32 MiB) refuses a declared or streamed oversize body with 413 before the application reads it; `ALLOWED_HOSTS` (comma list, `*.domain` allowed) refuses other Host headers with 400; both are validated at start-up, and production without `ALLOWED_HOSTS` warns. WebSocket messages stay limited to 64 KiB and 30 jobs/connections per user per minute.
**Forwarded headers.** Run the API as `uvicorn main:app --proxy-headers --forwarded-allow-ips <the proxy's private address>` (never `*` unless the API is reachable only through the proxy). The application does not use the client IP for any decision; the proxy does.
**Timeouts.** Proxy: header 10 s, body 15 s, send 30 s, upstream read 130 s (a model call can take that long), WebSocket 1 h idle; uvicorn `--timeout-keep-alive 30`. **TLS:** terminated at the proxy; upstreams on a private network only; never publish ports 8000/3000.
**Next.js token issuance:** per-person ceiling in the app (`TOKEN_ISSUE_PER_MINUTE`, in memory per process) plus the proxy's per-IP limit above.
**Pre-deployment gate:** `python ../ops/check_config.py --profile staging|production` (from `backend/`, with the deployment's environment) blocks demo mode, a non-production `APP_ENV`, missing auth/hosts/https origins, a short `METRICS_TOKEN`, a non-PostgreSQL database; warns about the degrade mode, embedded run execution, missing alert webhook/backup status. `ops/staging.env.example` is the template (placeholders only); a test keeps it valid.

## 18. Alerting that is actually delivered (sprint 4)

**What is live when `ALERT_WEBHOOK_URL` is set:** every API process runs `alerting.py` every `ALERT_EVAL_INTERVAL` seconds (default 30): 11 rules (unknown side-effect outcomes, approval backlog, no workers while runs wait, failing/interrupted runs, provider retry budget exhausted, Redis unavailable, DB pool near exhaustion, 5xx rate, latency, backup stale, restore verification failed) with severity (`page`/`ticket`), a `for` period before firing, ONE notification on firing, a reminder at most every 4 h, ONE resolved notification, Redis-based de-duplication across processes (falls back to "deliver anyway" if Redis is down), bounded delivery (3 attempts, 5 s each) and delivery-failure handling (a failed notification stays pending, is retried by the next pass and counted in `agentforge_alert_delivery_failures_total{rule}`). Payload: Slack-compatible `text` plus `alert`, `severity`, `status`, `since`; never a user, workspace, run, token or the webhook URL. Without a webhook nothing is evaluated and the rules in `ops/alerts/agentforge-alerts.yml` remain definitions for a Prometheus/Alertmanager you operate.
**Backup signals:** `ops/backup_job.py` (section 20) writes `BACKUP_STATUS_FILE` and a Prometheus textfile; the evaluator turns them into the two backup alerts.
**Verified:** 12 tests against a local disposable webhook receiver (state machine, flapping, repeat interval, failed delivery retried exactly once to success, two processes announcing once, dead Redis, broken rule isolation, real HTTP notifier with bounded retries and secret-free logs, background loop start/stop, backup status file) and a backup drill whose corrupt/truncated/mismatched archives fired the restore-verification alert and delivered one webhook message each. **NOT verified: delivery to any production receiver (Slack, PagerDuty, Alertmanager), on-call routing, silencing, escalation.** Per-process vs aggregated: the process-local counters feed each process's own view (a 5xx rate computed by one process sees only its traffic); the database gauges are global.
**Production configuration required:** `ALERT_WEBHOOK_URL` (https; a secret), `ALERT_EVAL_INTERVAL`, `BACKUP_STATUS_FILE`, `METRICS_TOKEN`, and a receiver someone watches. Send a test alert before relying on it (set a rule's condition by briefly creating an unresolved dispatch in staging).

**Sentinel support.** `REDIS_SENTINELS=host:port,...` + `REDIS_SENTINEL_MASTER` make the rate limiter and the provider coordination use the CURRENT master (`redis_client.py`, redis-py `master_for`; no custom re-discovery). **Failover drill (`bash ops/sentinel_failover_drill.sh degrade|closed`, 1 master + 1 replica + 3 sentinels, client inside the Docker network, real provider-coordination code):** the replica was promoted and the client recovered through it (measured client-side outage 36 s on a loaded machine with 5 s down-after, both modes). `degrade`: 307 of 307 slot requests were granted during the outage (per-process limits only: the global cap was NOT enforced); `closed`: 0 of 308 granted. **Independent workers under load (`tests/ops/load_test.py --workers N`):** API processes run `RUN_EXECUTION=api-only`, workers execute runs; shared rate-limit budget and global provider cap held across processes (measured concurrency 4 = cap 4); a worker hard-killed (process tree, no cleanup) while it owned runs left them to lease expiry: the runs ended `partial`/`failed` with `interrupted` (never stuck), the replacement worker and the other worker continued, **0 duplicate real sends** (mock counts per idempotency key), no run or execution left running; lost responses (20% of sends accepted but never answered) became `side_effect_outcome_unknown` with exactly one real send each; a Redis outage of 9 s during load caused 0 request errors (degrade: counted, provider concurrency peaked at 6 over the cap of 4 while Redis was down; `PROVIDER_REDIS_DOWN=closed`: the cap held at 4 and nothing failed, p95 end-to-end 20 s because requests waited for Redis).
**Operational rule:** after a worker crash a run is NOT resumed automatically: it is recovered as `interrupted` once its lease lapses (default lease TTL in `LeaseConfig`) and a person retries it; finished tasks are reused and a side effect that may have happened blocks the retry until reconciled.

## 22. Redis outage, failover and the provider concurrency cap: the policy since sprint 4.1 (supersedes the "degrade by default" statements in sections 10, 11 and 19)

**The finding that drove this.** In sprint 4 the DEFAULT mode (`degrade`) granted 307 of 307 provider slots during a Redis outage and provider concurrency reached 6 against a configured global cap of 4: the application kept running and silently stopped enforcing the cap. A cap that is not enforced must never be presented as one.
**What now happens, by consumer.**
| Shared state in Redis | Redis unreachable | Redis server changed/restarted (failover, restart, restore) |
|---|---|---|
| **Provider global concurrency cap** (the invariant) | DEFAULT `closed`: admission REFUSED (requests wait `PROVIDER_ADMISSION_WAIT`, then fail `rate_limited`; the model is never called). `degrade` (explicit opt-in only): per-process limit, cap NOT guaranteed | admission QUARANTINED for one lease term (`PROVIDER_LEASE_SECONDS`, default 90 s) for EVERY process including ones started after the move, because slot accounting may have been lost; `degrade` falls back per process |
| Provider cooldown | no shared cooldown (each process still honours its own 429s) | forgotten (the next 429 sets it again) |
| Per-user rate limits | per-process counters (still bounded, no longer shared); gauge `agentforge_rate_limit_shared_enforced` = 0 | windows are fresh |
| Run leases, ownership, fencing, side-effect dispatch, approvals | **not in Redis**: unaffected. They live in PostgreSQL | unaffected |
| Short-term chat memory (legacy) | "History unavailable" warning, features continue | same |
**Server-move detection.** The admission script compares the Redis server's `run_id` with `provider:origin`. A different value (promoted replica, restarted or restored server) writes `provider:quarantine` for one lease term and refuses admission everywhere until it expires. Residual risk: if `provider:origin` is lost together with the slots (a flush, or a replica that never received either) the move is indistinguishable from a first start.
**Replica acknowledgement (automatic with Sentinel).** After a grant the coordinator issues `WAIT 1 100`: if a replica exists and did not acknowledge, the slot is withdrawn and admission refused; if NO replica is connected, nothing could lose the lease in a failover and the grant stands. Run Redis with `min-replicas-to-write 1` and `min-replicas-max-lag 5` so the master stops accepting writes when no replica is in sync (bounds what a failover can lose). Replication stays asynchronous: this narrows the loss window, it does not close it.
**Visibility.** `agentforge_provider_admission_total{decision,reason}` (granted/full/refused/degraded; ok, cap_reached, store_unavailable, server_moved, replica_ack_missing, no_replica), `agentforge_redis_unavailable_total`, gauge `agentforge_provider_global_cap_enforced` (0 = not enforced right now; alert `AgentForgeProviderCapNotEnforced`, page, 1 minute), an ERROR log line when a server move is detected, a warning at start-up when `degrade` is selected.
**Measured (disposable Redis/PostgreSQL, 2 API processes + 2 workers, stub model, global cap 4; concurrency measured by an INDEPENDENT per-process log of provider-call start/end, 0 unmatched lines in every run):** baseline 4; **default policy, Redis stopped for 9 s: peak 4 (cap held), 0 duplicate sends**, 77 plans completed in 170 s, 6 requests failed `rate_limited` and the 95th-percentile end-to-end time was 47 s while admission was refused (the availability price of the invariant), service recovered fully; explicit `degrade`: peak 6 (cap exceeded) with all 42 runs succeeding; worker hard-kill under the default policy: peak 4, 0 duplicates, nothing left running.
**Sentinel drill (`bash ops/sentinel_failover_drill.sh closed|degrade ip|hostname [lose-lease]`, 1 master + 1 replica + 3 sentinels, real client and coordinator, global cap 1 held by a "request" that keeps running):** before the failover the replica HAD the lease (YES); Sentinel promoted the replica; the client recovered in 6.0-8.6 s (IP and hostname addressing); the lease was present on the promoted master (YES) when replication had caught up; with the `lose-lease` variant (the slot deleted on the replica just before the failover to simulate the asynchronous gap) it was absent (NO) and **the default policy still granted 0 admissions while the original holder could be running** (the quarantine), resuming normal service about 87 s after the start (one lease term after the move was detected); the same failure under `degrade` granted 418 admissions in violation of the cap. The sprint-4 observation "lease lost after failover" was NOT reproduced when replication was caught up and is attributed to that drill having no `min-replicas` setting, no replica acknowledgement and a late check; it is not proven to be the only cause. **Hostname finding:** with Sentinel monitoring a master by NAME, a stopped container's name stops resolving and Sentinel's blocking DNS lookups keep it in TILT, so it never failed over; with a static host entry in each sentinel (or by IP) it works. Use IPs or stable DNS that keeps resolving.
**Stale owners.** Two different "owners" exist and they are protected by different layers: (1) a PLAN-RUN owner (a worker) that lost its lease is fenced by the DATABASE (run lease generation checked in every write: PostgreSQL tests of a stale worker unable to start, finish or re-open a dispatch, concurrent retries, takeover; 64 of 64 passed on the final tree); Redis plays no part; (2) a PROVIDER-SLOT holder whose lease was lost by Redis cannot cause a cap violation because new admissions are refused until it can no longer be running (the quarantine above; real-Redis script tests and the `lose-lease` drill). A new owner is admitted normally after the quarantine.
**Operational advice.** Keep the default (`closed`) unless exceeding the provider quota is acceptable. Size `PROVIDER_LEASE_SECONDS` above your longest provider call plus margin; a longer value lengthens the refusal after a failover. Alert on `AgentForgeProviderCapNotEnforced`. Run Redis with replication and `min-replicas-to-write`, persistence on, Sentinel by IP. **Not tested:** Redis Cluster (unsupported), multi-replica elections, network partitions with a live old master, a failover during an in-flight admission burst beyond the drills above.
