# Recovery drills (measured locally) and the staging execution runbook

**Read first.** Everything in section 1 was measured on one developer machine (Windows 11 host, Docker Desktop, PostgreSQL 16, Redis 7, tiny databases) or in CI containers. These are **local** numbers: they prove the mechanisms work and give a lower bound, they are **not** staging or production RTO/RPO. No staging environment has been authorised or accessed; section 2 is the runbook to execute once one is.

**RTO and RPO.** What is measured: client-visible Redis/Sentinel failover outage (6.3 s), worker-loss takeover without loss (bounded by the run lease), backup and restore of a tiny database (seconds), PITR correctness (0 committed rows lost up to the target instant). **What is NOT measured and must not be quoted:** restore time at production data size, an end-to-end RTO of the whole service (API + workers + edge + data stores) after a regional or host failure, and an RPO for an unplanned primary loss (the un-archived WAL tail is bounded by `archive_timeout`, 5 s in the drill, but a loss of the primary was not injected). Sentinel does not protect against losing the only copy of Redis; PostgreSQL remains the system of record.

## 2. Staging execution runbook (UNEXECUTED; requires the owner's explicit authorisation and access)

**Prerequisites the owner must provide:** an authorised staging environment (separate from production, no production credentials); a staging secret store entry built from `ops/staging.env.example`; PostgreSQL 16 with TLS and WAL archiving permissions (a backup/restore role and an archive target); Redis, preferably Sentinel (3 sentinels); at least 2 API and 2 worker hosts or processes; the edge (nginx config with a real certificate and the real `ALLOWED_HOSTS`/`CORS_ALLOWED_ORIGINS`); a non-production webhook receiver and, for D074, the on-call route to test; Resend **sandbox** key and an authorised sandbox recipient (D073); an authorised model key and a spending cap if the live-model run is wanted; a rollback owner and a maintenance window. Before each destructive drill the executor asks the owner for confirmation.

**Steps (each records start timestamp, recovery timestamp, observed downtime, data loss, recovered records, duplicate-dispatch result, command, exit code, limitations):**

1. Configuration gate: `python ../ops/check_config.py --profile staging` prints `CONFIG GATE PASSED`.
2. Data stores up; `/ready` 200 on every instance; one authenticated `/metrics` scrape.
3. `python -m alembic upgrade head`; `verify_schema_version`; confirm head `0017_invitations`.
4. Edge: `bash ops/edge_drill.sh` against the staging nginx config in a scratch environment, then the same checks with curl against the real hostnames (HTTP/1.1 WebSocket upgrade, 413, Host refusal, `/metrics` hidden, `X-Forwarded-For` overwritten).
5. Monitoring: set `ALERT_WEBHOOK_URL` to the authorised receiver; deliver one TEST alert end to end; confirm de-duplication with two API processes; confirm the on-call route pages a person (D074 evidence). Deploy `ops/alerts/agentforge-alerts.yml` and an external uptime check.
6. Backup: run `ops/backup_job.py`; confirm a verified restore and the two metrics; run the failed-restore variants.
7. PITR: restore to a chosen instant into a new instance; **time the restore** and record the data-size; check row counts either side of the instant.
8. Smoke: sign in; create a workspace; invite a second account; run the starter workforce plan; approve; see the run succeed with its cost.
9. Resend sandbox (D073, needs the owner's go-ahead for the real external call): one approved `email.send@1` to the sandbox recipient; record the provider response, dispatch state, external reference; then the unknown-outcome path (provider response dropped or an authorised failure injection) and the reconciliation; record that no key lookup exists.
10. Failure drills, one at a time: kill a worker mid-run (record takeover time, duplicate sends); stop Redis and restart it (record refused admissions and recovery time); Sentinel failover (record client outage); stop the primary PostgreSQL and promote or restore (record **end-to-end RTO** and **RPO**).
11. Load: `tests/ops/load_test.py` sized to the staging hardware, with the real model only if authorised and capped.
12. Rollback rehearsal: deploy the previous release, confirm schema compatibility (migrations are forward-only: roll back the application, not the schema), and record the time.

**Rollback plan.** Application: redeploy the previous image; workers drain on SIGTERM (running tasks are recorded `interrupted`, leases released). Schema: forward-only; `0017_invitations` only adds a table, so the previous release runs against it unchanged; restoring data uses the verified backup / PITR. Edge: keep the previous nginx config for an instant revert.

**Recording.** Fill in the table of section 1 for staging with the real measurements and label the document "staging". Never copy a local number into a staging row.
