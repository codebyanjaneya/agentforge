## Sprint 4.1 (2026-11-20/21): final reliability closure (supersedes the sprint-4 Redis statements above)

- **Policy change (D071 amendment, status unchanged: Directed, owner confirmation pending):** the sprint-4 default `PROVIDER_REDIS_DOWN=degrade` silently dropped the global provider cap (307/307 slots granted, concurrency 6 vs cap 4). Now the default is `closed` (admission refused whenever the shared accounting cannot be trusted); `degrade` is an explicit, disclosed opt-in (warning, `provider_admission_total`, gauge `provider_global_cap_enforced`, alert `AgentForgeProviderCapNotEnforced`). A Redis server change/restart quarantines admission cluster-wide for one lease term (`PROVIDER_LEASE_SECONDS`, default 90 s) via a `run_id`/`provider:origin` comparison inside the admission script; with Sentinel a grant must be replica-acknowledged unless no replica exists. Run leases/fencing/dispatch are in PostgreSQL and unaffected.
- **Evidence:** 2 API + 2 workers, stub model, cap 4, exact independent measurement: default policy under a 9 s Redis outage held peak concurrency at 4 with 0 duplicate sends (price: 6 requests failed `rate_limited`, p95 47 s, full recovery); explicit degrade peaked at 6. Sentinel drills (IP, hostname, lose-lease, degrade): promotion in 6-8.6 s, lease present when replication caught up, and with the lease deliberately lost the default policy still granted 0 admissions while the holder could be running (418 violations under degrade). The sprint-4 "lease lost after failover" observation was not reproduced and is attributed to that drill lacking min-replicas/ack/late check (not proven the only cause).
